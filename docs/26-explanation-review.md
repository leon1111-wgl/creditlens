# 新增解释怎样单独交接

研究底稿已经确认之后，又找到了公司的经营解释。这份新材料需要有人决定是否收录、说明用途，再交给另一人看。旧底稿的确认只针对当时的内容，不能自动覆盖后来补充的说法。

v0.15 新增 `/explanation-reviews` 页面，从“研究任务 → 公司解释”进入。先选择一份已复核的研究，再建立解释补充底稿。它保留原研究及其复核快照，新增自己的采用意见、提交版本和复核记录。

## 一份补充稿怎样走完

1. 分析员查看公司原文概述、实际期间、相关现金流和披露精度，选择“作为公司陈述收录”“不采用”或“待补证据”，填写理由。
2. 保存核查范围，说明哪些问题仍没有证据。只有原研究已采用两期现金流，才可收录与它们关联的解释。
3. 提交时再检查原研究版本和来源登记，固定这一版材料与处理意见。来源变了就停止提交，提示重新建立绑定材料的补充稿。
4. 另一身份确认处理意见与范围，或退回补充。原研究和本补充稿的制作参与者均不能自审；原研究的复核员可以复核自己没有参与制作的补充稿。
5. 退回后重新保存、提交，得到新快照；以前提交过的版本和对应复核记录仍可下载。

确认“待补证据”或“不采用”，表示复核员认可这一处理及其范围。它们不会变成“已收录”，更不会变成“原因已证实”。即使收录了公司解释，也只写“公司将变化归因于……”。

## 输入、正确标准、错误与恢复

| 模块 | 输入 | 正确标准 | 常见错误与发现／恢复 |
|---|---|---|---|
| 建立补充稿 | 已复核原研究 ID、预期版本、快照摘要、幂等键 | 同一事务中核验原研究批准状态并保存完整父导出；身份取自服务端 | 旧版本或未批准返回409；跨租户404；同键同请求返回已有稿，换内容拒绝 |
| 证据与决定 | 服务端登记的解释、数值核对与逐条处理理由 | 来源、两期实际日期、金额及父稿采用决定相互对应；客户端不能提供来源或提升支持范围 | 未采用的数字不允许关联收录；多余字段422；原始决定和缺口可查，重新核查后另建适用稿 |
| 提交与复核 | 预期 revision、说明、复核时的快照 SHA-256 | 冻结证据与决定；复核必须对应这份快照，参与制作的用户不能自审 | 并发旧版本409，自审403，短理由422；刷新后重新处理，退回修改保留旧快照 |
| 历史读取与导出 | 补充稿及已提交快照 ID | 不依赖当前来源目录；原研究与旧子稿不被新提交改写 | 内容／摘要绑定失败就停止导出；保留原记录，排查哪一层不一致，不自动修补摘要 |

## 技术实现与验证边界

`ExplanationReviewStore` 复用原研究的 SQLite 连接和事务，在独立表中保存补充稿、提交快照、角色与处理记录。写入检查预期版本；重复建立由租户、请求键、请求内容及主体共同约束。原研究和快照表只有读取，没有写入。

`explanation-evidence-1` 将父导出、公司陈述、原文定位、来源摘要、数值和采用状态保存在同一份证据包中。客户端只能提供处理决定、理由和范围；`company_statement_only` 及 `independently_verified=false` 由服务端固定。数字使用局部 Decimal 上下文复算，避免其他代码修改全局精度后影响结果。

离线核验逐层检查父导出、证据内容、金额转换、采用前提、提交人、贡献者与复核绑定，不读取当前数据库或来源目录：

```powershell
python scripts/verify_explanation_export.py artifacts/explanation-review-demo.json
python -m unittest discover -s tests -p "test_explanation*.py" -v
```

这些检查说明文件内部及登记版本一致，不是数字签名、外部存证或人员真实性验证。管理员同时重写记录与摘要的威胁仍需要外部存证机制。当前版本只支持已登记的微软 FY2025 公司解释及相应材料包，尚无通用附注抽取、自然语言因果判断或新的模型评测。
