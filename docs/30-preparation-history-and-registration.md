# 旧准备记录，与现在的材料分开核对

同事打开一份旧准备记录时，需要回答两个问题：这份导出里的版本、页数和判定是否互相一致；它当时使用的材料登记，与现在是否仍然相同。旧记录“当时准备通过”，不能代替第二个问题。

现在材料准备页会并列显示历史尝试和当前登记检查。历史失败仍按失败保留，历史通过也不会被改写；当前清单改变或不可读时，页面说明需要重新核对，原导出仍可查看。

## 四句话验收

| 模块 | 输入 | 正确标准 | 最可能怎样出错 | 怎样发现与恢复 |
|---|---|---|---|---|
| 离线记录核验 | 单次准备导出 JSON | 精确契约、身份关系、摘要、页集、计数与状态互相一致 | 只改通过状态、计数或来源，忘记关联字段；重复 JSON 键覆盖旧值 | 固定错误代码和字段路径；回到原导出重新取得文件 |
| 当前登记检查 | 已核验的旧摘要和当前本地清单 | 指向同一尝试，区分所选文档变化、整体清单变化和当前不可读 | 把清单编辑说成 PDF 修订，或材料缺失时仍显示旧的绿色状态 | 返回变化字段和原因，重新取得可靠登记后再检查；不覆盖历史 |
| 页面交接 | 某次尝试及本次检查响应 | 历史版本、当前状态分别可见，切换身份／尝试后旧结果不能回填 | 慢响应覆盖新的选择，检查失败仍能导出旧检查 | 请求序号隔离，先清空，失败时保留历史并禁用本次检查导出 |

## “内部一致”能够说明什么

离线核验无需原始 PDF、OCR 正文、数据库或网络。它复算导出中的摘要，并检查已保留的字段关系：任务和尝试是否对应、重复页和缺页统计是否成立、逐页错误与整组状态是否冲突、计数是否匹配、规则版本是否受支持。

它不能从这些摘要重新识别文字，也不能证明文件出自真实处理人。若有人完整重写一份自洽记录并重算全部摘要，仍可能通过。因此结果使用 `internally_consistent`，不会叫“验真”“防篡改认证”或“OCR正确”。失败的历史尝试同样可以内部一致。

## 当前检查怎样解释

| 状态 | 含义 | 下一步 |
|---|---|---|
| `matching_registration` | 所选材料及整体登记仍匹配 | 还须历史准备通过、规则版本匹配、历史页集及逐页登记一致，才能继续内容核对 |
| `document_registration_changed` | 所选文档的登记包或绑定变化 | 查看具体字段，以新的登记重新准备；不自动迁移旧判定 |
| `inventory_changed` | 所选文档登记相同，但整体清单变化 | 保守要求检查变化范围，不能据此声称该 PDF 已修订 |
| `document_not_registered` | 当前有效清单没有该文档 | 查明登记移除或替换原因；不等于企业没有披露 |
| `registration_unavailable` | 当前清单不可读、校验失败或检查期间变化 | 修复登记后重查，历史记录仍独立可读 |

状态说明登记绑定的比较，具体阻断还看 `reason_code`。例如登记摘要相同但历史页集、图像摘要或事实编号不一致时，仍阻断继续处理，页面优先显示这一原因。

检查在读取前后比较登记摘要，用于发现检查期间变化；它不是文件系统锁，也不保证检查完成后材料永远不变。`ready_for_content_review` 仅表示可继续内容核对，所有结果仍保持不可查询、不会自动批准。本轮未验证实际 PDF 和图片字节，也未传播到搜索缓存或审批状态。

## 本地复查与接口

```bash
# 核验浏览器下载的单次导出，不依赖当前登记
python scripts/verify_preparation_export.py path/to/creditlens-preparation-attempt.json

# 同时检查本地当前登记
python scripts/verify_preparation_export.py path/to/creditlens-preparation-attempt.json --check-current

# 显式选择公开合成复演中的第三次尝试
python scripts/verify_preparation_export.py artifacts/document-preparation-replay.json --attempt-index 2 --check-current

# 在隔离的小型登记副本中复演变化；同名输出不覆盖
python scripts/evaluate_preparation_history.py
```

CLI 限制本地文件大小，拒绝重复键、非有限数值和无效结构。选择复演包中的一个尝试时，只核验该项，不替其他尝试或包内叙述背书。退出码0表示导出核验已完成；当前登记是否可用，应读取单独的 `applicability.status` 和 `ready_for_content_review`。

工作台新增 `GET /api/document-preparation/tasks/{id}/applicability?attempt_id=...`，先验证工作区访问权限，再读取当前登记。响应中分别包含 `verification` 和 `applicability`；旧的历史导出接口与字节不改变。可以单独导出本次检查，便于说明为什么旧准备结果暂时不能沿用。

本轮复演沿用第26轮的三份合成尝试，在独立小目录中编辑清单备注、登记包标题和无效 JSON，检查不同状态。这些变化用于测试，不是 NVIDIA 发布了新的修订公告，也不增加模型样本数。实际结果见[制作记录](iterations/2026-10-26-27.md)。
