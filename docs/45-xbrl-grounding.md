# XBRL 对照：以发行人自己的 XBRL 标签为答案键的取数基准

v0.34.0（2026-11-10）。这是项目第一个在**未参与开发的发行人**上测量的文档取数结果：

- **答案键 = 发行人自己的 XBRL 标签。** 美国发行人的 10-K 是 Inline XBRL：报表上每个数字都由发行人打了概念、上下文（期间与维度）、单位、decimals、scale 与 sign。
- **取数只看图像。** 报表页由 Chromium 渲染成图片，OCR 只接收图片；HTML 文字只用来选页和建答案键，从不进入取数。
- **干净渲染页，不是扫描件。** 结果说明的是 OCR 加版面规则在清晰页面上的表现，不代表扫描件、手机照片或发行人 PDF。

页面：[XBRL 对照](https://leon1111-wgl.github.io/creditlens/grounding.html)（本地服务 `/grounding`）。

## 评分规则

图像一侧在识别完成之后、不看答案的前提下读出：

- **单位**：标签上方最近的 “(In thousands / millions / billions …)” 表头（允许 “Dollars in”“Amounts in”“$ in” 前缀）。
- **年份列**：上方最近的一行 2–6 个年份表头（“2025”“December 31, 2025”“Fiscal 2025” 等），列边界取表头中点（同 `table_lookup.lookup_layout_column`）。
- **股数与每股行**：行名或其上方最近的纯文字标题（最多越过 4 行金额行，如 “Earnings per share:” 下的 Basic、Diluted）提到 shares、per share 或 par value 时，不套用表头量级，记为未作答。

然后按标签框取 OCR 片段（项目原有规则 visual-evidence-1）：片段覆盖标签框 35% 以上，或片段中心落在框内，即为“定位命中”。随后依次检查：置信度不低于 0.90；片段越出框不超过 8 pt；一格只有一个片段；格旁 8 pt 内没有分离的括号、负号或数字碎片（word-evidence-1）；文字是完整金额（table-lookup-1 的严格语法：千分位、可带 `$`、括号负数）。任一不满足即**未作答**，并记下原因。

| 结果 | 条件 | 页面颜色 |
|---|---|---|
| 一致 | 数位、括号符号、量级、年份列四项都与答案键相符 | 绿框 |
| 冲突 | 读出了完整读数，但至少一项不符 | 红框 |
| 未作答 | 读数不完整，规则停下 | 琥珀虚线框 |

答案键的细节：

- 数值按标签的 ixt 格式解析（`num-dot-decimal` 去千分位；`fixed-zero` / `zerodash` 为 0；其他格式不计分并单列）。
- **符号以印刷括号为准**，XBRL sign 属性并列显示。有的概念印成扣减项“(500)”，标签值却是正数；这种差异只说明列报方式，不算图像读错，页面也照此说明。
- **年份列**：期间事实取结束年份，时点事实取其所在年份。若时点恰是同页某个期间开始的前一天（现金流量表上的“期初现金”），同一事实会印在两列（上一年的期末、下一年的期初），两列都算对。
- 定位框是 `ix:nonFraction` 元素本身的矩形，不含旁边的 `$`。

评分代码：`creditlens/xbrl_grounding.py`；运行与发布：`scripts/xbrl_grounding.py`；规则与参数：`configs/xbrl-grounding.json`；测试：`tests/test_xbrl_grounding.py`、`web/tests/grounding.test.ts`。

## 数据通道：为什么经互联网档案馆

SEC 要求自动化访问声明身份并控制频率。本基准在 GitHub Actions 上向 `data.sec.gov` 与 `www.sec.gov` 的请求一律得到 HTTP 403 “Your Request Originates from an Undeclared Automated Tool”，与 User-Agent（含联系地址）和请求头无关（2026-11-09，运行 42709826308、42710194611，诊断运行 42710474268、42710749950；运行器出口地址属 Azure）。因此：

- 不向 SEC 发请求，也不在开发机上代为获取；
- 只读互联网档案馆**已有**的 SEC 原地址抓取，不触发新的抓取；
- 每个文件按 CDX 记录的 SHA-1 摘要核对字节；HTML 还须自报同一 CIK 与 10-K 文件类型；
- 页面与报告同时给出 SEC 原地址、accession、档案抓取时间和档案地址；图片下方的灰条印有 SEC 地址与 accession。

这改变了总体：原规则 a（`0354141`）用 SEC frames 与 submissions 接口，这两类地址没有档案抓取；规则 b（`1005fa2`）在任何保留集运行之前改用 SEC 2026q1 Financial Statement Data Set。没有档案抓取的候选按规则跳过并记录，这会偏向被抓取较多的大公司。

## 怎样重跑或加一家发行人

合并后在 Actions 中手动运行 “xbrl-grounding”：

- 重跑保留集：`mode = heldout`。规则不变时，候选顺序不变；档案抓取若有新增，可能选到不同的公司，报告会记录。
- 加一家（不计入保留集）：`mode = added`，`filings = cik:accession:主文件名`，例如 `320193:0000320193-25-000079:aapl-20250927.htm`（主文件名见 EDGAR 的提交索引页）。该文件须已有互联网档案馆抓取。
- 合并前：在任意 `xbrl-run/*` 分支上改 `configs/xbrl-grounding-dispatch.json` 后推送。

例：开发者自测用 `added` 模式跑了可口可乐 FY2025 10-K（`21344:0001628280-26-010047:ko-20251231.htm`，不在保留集里，运行 [42718740819](https://github.com/leon1111-wgl/creditlens/actions/runs/42718740819)，提交 `21c9cc5` 加一处调度文件改动）：4 页、264 个事实，一致 220、冲突 0、未作答 44（越出标签框 30、股数行 12、无片段 2），运行内的 `verify-saved` 通过。这次结果不计入保留集，也没有发布页面图片。

结果在运行摘要与产物 `xbrl-grounding-<label>`（`report.json`、页面 PNG、可发布的 `site/`）中。把 `site/` 复制为 `creditlens/grounding/`、`report.json` 复制到 `artifacts/xbrl-grounding/` 并更新 CI 中的 `verify-saved` 路径，即可在页面展示。

不需要 OCR 或网络的复核（CI 已运行）：

```bash
python scripts/xbrl_grounding.py verify-saved artifacts/xbrl-grounding/heldout-first-run.json --site creditlens/grounding
```

它用保存的答案键与 OCR 片段重新评分，逐条比对保存的结果与汇总，并核对页面图片与标签文件的哈希。

## 边界

- 干净渲染页比扫描件容易；Chromium 的字体替换也使页面与发行人 PDF 不同。合成退化与真实扫描件没有测。
- 发行人少、页面少，数字聚集在少数几家公司里，彼此并不独立；不报告置信区间。
- 没有人工复核；XBRL 标签本身也可能有误，这里把它当作发行人自己的答案。
- 只测“图像能否读回已标注的数字”，不测打标签（概念对应）本身，也不测附注、图表或跨页续表。
- 规则只在开发文件（苹果、微软）上改过两处，见下文；其中标题规则在保留集上过宽（见“未作答的原因”）。保留集首轮之后的任何修改都不再是盲测。
- 页面框的颜色只说明图像读数与标签的关系；“定位召回”把覆盖标签框的整行片段也算作命中（113 项行名中的数字即是如此），不是数字级定位精度。
