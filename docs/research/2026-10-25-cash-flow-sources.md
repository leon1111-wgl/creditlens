# 经营现金流调节资料：把合计拆回原表

日期：2026-10-25。资料包：`msft-aapl-cfo-bridge-fy2025`。

已有研究底稿能显示经营现金流增加或减少，但仅看合计，复核人仍需打开财报查明这个变化由哪些会计项目组成。本轮补齐微软和苹果 FY2025 官方报告里的经营现金流调节行，让后续计算可以逐项展示、相加核对、跳回原页。

这份资料负责来源与口径。变化分解由独立的计算模块完成。调节项提供的是会计恒等式中的贡献，不是已经证实的经济原因，也不输出预测或投资建议。

## 口径怎么保留

分组直接跟随原表分区，字段 `role` 只有四类：

- `net_income`：净利润。
- `reconciliation_adjustments`：净利润调节项。
- `operating_assets_and_liabilities`：经营资产负债变化。
- `cfo_total`：报表经营现金流合计，不再作为组成项相加。

苹果的 `Other` 原文没有声称全部属于非现金；微软的折旧、摊销及其他也属于混合行。因此调节部分统一称“净利润调节项”，不强行细分为全部非现金。经营资产负债部分包含长期项目、所得税和未赚取收入，不能统称狭义营运资本。

所有金额保留 `raw_value` 和 `signed_value`。括号按负数处理，未取绝对值，也不借用旧资本开支行的流出绝对额转换。每个组成项都有稳定的全局 ID、原文标签、金额框、行名框、年份框、期间框、单位框，以及相应子分区的上下边界。

合并口径沿用已人工核验的 Note 1 依据：微软第 55 页、苹果物理第 37 页的合并基础，以及本页现金流表的完整行名。只声明报表列示的合并经营现金流总额，持续经营和终止经营的进一步划分仍为 `unknown`。

## 提取与拒绝条件

`scripts/build_cash_flow_bridge.py` 是固定材料的离线适配器。它先验证两个完整 PDF 的注册哈希，再用现有 PDFium 可见页面坐标转换提取数字文本；没有 OCR、模型调用、网络下载或按预期金额查找单元格。

适配器要求经营部分的全部行及两级标题按原表顺序出现。少一行、多一行、重复行、错列、无法读取的金额都会拒绝，不会因为所选子集恰好相加相等就忽略遗漏。年度列来自表头位置；参考金额不参与选择。

苹果同页存在多个 `Other`，并且还有以 `Other` 开头的资产、负债项目。仅按前缀查找时，首次构建明确拒绝了歧义。本次采用原表的“调节标题至资产负债变化标题”作为该组边界，保留所有原始行；没有用参考数值选择其中一行。其他组也保留对应子分区证据。

构建完成后才绑定旧研究材料中的 CFO 全局 ID，核对来源、公司、单位、期间和合计值。四个年度都要求带符号组成项之和等于报表合计。

`creditlens/cash_flow_sources.py` 的运行时入口只读取服务器固定路径；调用方不能指定 URL、材料路径或发行人。它校验固定 JSON 的规范摘要、严格字段、完整行清单和旧 CFO 绑定。JSON 缩进或换行可以改变，数值、标签或坐标变化会拒绝。运行时不依赖原 PDF，`raw_pdf_rehashed=false`；`build_pdf_sha256_verified=true` 只记录此次构建时的字节核对，不是文件真实性签名。

规范 JSON SHA256：`6e2835ffd2891258cc67aff2f46ff8f031c1000b9f9bbb04456655cc3e6d60a6`。规范化采用 Python `sort_keys=True`、`ensure_ascii=False`、紧凑分隔符和 `allow_nan=False`；这是规范 JSON 的哈希，不是磁盘原文件字节哈希。

## 重建方式

在已安装项目 PDF 可选依赖的环境中，将两份已登记 PDF 放入一个本地目录，文件名分别为 `msft-fy2025-10k.pdf`、`aapl-fy2025-10k.pdf`，运行：

```powershell
python scripts/build_cash_flow_bridge.py --pdf-dir .run/cash-flow-bridge-input --output .run/reproductions/cash-flow-bridge-v1.json
python -m unittest tests.test_cash_flow_sources
```

默认输出是新的本地候选文件。已存在的输出会拒绝，重跑应换一个本地文件名。脚本在读取 PDF 前检查输出路径，不允许写到 `data/`、`configs/`、`artifacts/`、输入目录或登记的页面预览目录，也没有强制覆盖开关。路径检查是防误覆盖措施，不是对并发恶意文件系统变更的操作系统沙箱。

新候选不会自动变成公开注册资料。需先复核，再单独登记资料包与规范哈希；本轮未修改任何旧事实包、OCR 规则、冻结模型结果或原页面文件。

## 实际验证与范围

- 真实 CPU 构建产生 52 个带符号事实；四个年度的加总残差均为零，合计分别是微软 FY2024 118,548、FY2025 136,162，苹果 FY2024 118,254、FY2025 111,482（单位均为百万美元）。
- 原页视觉检查确认行顺序、括号、年度列和分区；独立顾问以事先抄录的原表金额核对 52/52，再直接通过 PDFium 有界原文读取金额、行名、年份和单位共 208 个区域，全部一致。该复核未调用本构建器或文档提取帮助函数，也未运行 OCR。
- 16 项测试覆盖真实金额、原始分组、负号、重复 JSON 键、非有限数、文件上限、冻结资料或旧 CFO 改动、缺行与重复行、错列、歧义 `Other`、错误来源/期间/单位，以及写入公开目录前拒绝。
- 本轮是两个已观察、固定版式官方 PDF 的确定性资料提取。没有证明未知发行人的通用表格抽取准确率，也没有把会计分解验证为经济因果、预测能力或银行审批能力。
