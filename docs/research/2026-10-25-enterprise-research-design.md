# 下一阶段设计：完成一份可以交接的同行现金流研究

审阅日期：2026-10-25。实现依据为包含主分支 `0a2611d` 的工作区。本文是代码审阅与下一阶段设计，没有新增功能、模型结果或用户试用结论；不修改已冻结的文档规则和实验。

**下一阶段只打通一个任务：研究员比较两家同行、两期年度的现金流变化，找出可比较的数字和需要调查的原因，再把证据、计算、缺口及判断交给另一位同事复核。**

可以对外这样解释：CreditLens 正在建设一个给投研和风险团队用的研究工作台。研究员提出“这家公司现金流为什么变了，与同行相比有什么不同”，系统帮助整理材料、检查数字能不能放在一起比较、追查解释依据，最后形成同事能够接手的研究底稿。当前已有事实、文档核对、季度观察和复核基础；这份跨公司研究任务还需要把它们接起来。

## 一、先确定使用者要完成什么

使用者暂定为基本面研究员，接收者为同一团队的独立复核员。研究员要为一次研究讨论准备材料，决定哪些变化值得继续追查。最终交付是一份带快照的比较底稿，包含：

- 两家公司各自的经营现金流变化，以及能够成立的同行比较；不能比较的位置列原因。
- 资本开支按各自披露范围展示，明确是否包含无形资产、是否仅含持续经营业务。
- 每个数字的原文位置、版本、单位、期间和计算过程。
- 零到三个候选解释，以及支持、反驳或仍然缺少的材料；没有依据时允许不提出解释。
- 复核人的处理意见、未解决事项和下一位接手者需要做的工作。

这是从现有实现、实际文档失败及既有需求调研得出的产品假设，尚无机构客户访谈、工时节省或投资效果数据。验收时要检查能否完成这项研究和交接，不能只统计识别一致数。

P0 的材料边界是**两家同行、两期完整年度、经营现金流与资本开支两类主指标，以及为解释变化所必需的附注和管理层讨论片段**。使用同一币种，先不做自动换汇、公司交易执行、组合优化或开放式自动研究。同行集合由研究员明确选择并记录理由，不由模型临时挑出“效果最好”的公司。

AMD 与 NVIDIA 可以作为候选，但现有包不能直接组成合格比较：两个包的最新年度结束日相差约一年；AMD 当前选的是持续经营现金流和资本开支，NVIDIA 的资本开支标签包含固定资产及无形资产。还需要取得期间相近的年度材料，并核验业务范围。不能因为都叫“FY2025”或都属于半导体行业，就把数值排成高低榜。

同轮调研对这个选择提供了三个具体参照：[产业合作调研](2026-10-25-hku-industry-projects.md)中的尽调与时间线配方启发“任务、来源、冲突、人工检查、交接”的组织方式；[团队项目调研](2026-10-25-hku-team-projects.md)中的 OHRBench 提醒将识别、检索、回答分层验收，TRivia 则可留作表格结构实验候选。它们不证明本项目已有合作、用户效果或模型增益；研究基准的数据许可也不能自动延伸到企业使用。

## 二、实际代码有哪些基础，断点在哪里

以下是本轮读取实现后的判断，不把文档中的计划视为现有功能。

| 研究步骤 | 已有实现 | 下一阶段缺口 |
|---|---|---|
| 保存事实与原页 | [diligence.py](../../creditlens/diligence.py) 的 `Fact`、`PdfLocation` 保留原值、单位、期间、来源及定位 | `Fact` 没有结构化的持续／终止经营、合并／分部、资本开支覆盖范围；标签中的口径不能替代机器可检查字段 |
| 检查图文是否一致 | [visual.py](../../creditlens/visual.py)、[word_evidence.py](../../creditlens/word_evidence.py)、[date_evidence.py](../../creditlens/date_evidence.py)；[发行人评估](../../creditlens/issuer_evaluation.py) 可冻结和复算三法结果 | 这些是独立只读实验，尚未自动成为研究事实的采用条件；“一致”也不是人工批准 |
| 区分来源日期 | `IssuerSource` 分开申报事件、精确文件发布时间、获取时间和历史版本证明 | 不同来源契约尚未统一。旧 `Source` 需要 `published_at`，不能为了导入未知日期材料而填一个看似合理的日期 |
| 查看时间变化 | [temporal.py](../../creditlens/temporal.py) 支持单公司、单财年、整月季度；累计差分标记待复核 | 没有多公司多年度面板、修订链和周历季度适配；`basis_id` 主要检查同包的一致性，并不是跨公司会计概念映射 |
| 形成研究视图 | [research.py](../../creditlens/research.py) 标明非实时、历史版本未验证；`/api/research/quarters` 只允许微软 FY2025 样例 | 不能选择同行、保存研究问题或共享一份多公司任务快照 |
| 算指标 | `analyze_pack()` 使用 Decimal、单位和期间检查；[因子导出](../../scripts/export_factors.py) 保留公式和来源 | 当前输出是观察指标，没有预测标签；简化 FCF 不能直接用于范围不同的新材料 |
| 查证据与调用模型 | [core.py](../../creditlens/core.py) 有 FinQA 页内 BM25 和受限算术；[planner.py](../../creditlens/planner.py) 有本机模型计划接口 | 尚无跨公司文档库检索、解释性回答评测或真实研究 Agent 完成率；模拟传输通过不代表模型任务有效 |
| 提交与独立复核 | [workflow.py](../../creditlens/workflow.py) 有租户、角色、幂等建案、事务内版本检查、独立复核和导出 | 服务接收的是单个 `CasePack` 信用底稿，不是跨公司研究任务；需要新任务契约，不能把所有公司硬塞进一个发行人 |

还有一个接入时必须显式处理的差异：`core.eligible()` 和 `analyze_pack()` 使用披露日期不晚于截止日；季度模块使用披露日次日开放。新研究任务必须选定并保存自己的可得时间策略，不能让不同工具各用一个默认值。旧实验和旧案例继续按原版本解释，不在整合时悄悄改变其结果。

## 三、用户实际怎样完成这份底稿

| 环节 | 用户看到什么、能做什么 | 系统应该执行的动作 |
|---|---|---|
| 1. 建立任务 | 写研究问题，选两家公司、两期年度和资料范围 | 保存同行选择理由、截止策略、指标范围和任务版本；列出尚缺材料 |
| 2. 核对材料 | 同一屏查看来源、原页和识别疑点 | 按文件哈希绑定证据；不同读取结果和原文各自保留。冲突不能由选择另一识别方法自动消失 |
| 3. 确认能否比较 | 看到“可以比较”“仅供并列查看”“缺资料／被阻断” | 比较期间、天数或周数、币种、持续经营范围、合并范围和资本开支定义；缺项不填零 |
| 4. 查看变化 | 看各公司变化表，点击任意数字进入原文和算式 | 用固定公式计算绝对变化；上期为零或负数时不输出容易误解的常规增长率。不可比公司不参与高低排名 |
| 5. 检查解释 | 写入候选解释，关联附注或现金流调节表 | 把“数字变化”“管理层说法”“研究员推断”分开；逐项列支持材料、相反材料和缺口 |
| 6. 固定研究结果 | 保存本次快照，预览比较底稿 | 固定数据版本、采用的事实、规则、计算、引用和假设状态。未解决部分以明确缺口交接 |
| 7. 独立交接 | 另一身份核对后确认或退回，并分配下一步 | 确认的是研究底稿及其限制。后续材料只创建新版本和受影响项目，旧底稿保持可回看 |

第一版允许研究员手工选择解释片段、填写假设；数字和引用由模板生成。不能把自由文本有一个引用链接，等同于该引用已经支持整段解释。

例如，假设“现金流下降主要来自应收款增加”，验证首先需要现金流调节表的应收变动，以及相关披露范围。只有年度 CFO 总额时，应输出“缺少应收变动依据”，而不是补一段听起来合理的原因。找到管理层的类似表述后，也应写成“管理层披露的解释”；只有两家公司两期数值，不能据此确认因果关系或预测能力。

### 当前材料与历史时点分开使用

P0 默认采用 `current_verified_materials`：研究当前已取得并核查的材料，展示当前报告中的比较列及其重列说明。任务保存材料冻结时间；历史财务期间不意味着这些字节在历史上已可得。

`historical_as_of` 是另一个明确模式。需要有可得时间和版本依据才开放；无法证明某个资产版本在截止时点前可得，就返回 `historical_version_unverified`。仅有申报事件、网页今天可以访问、或当前报告列示了往年数据，都不足以自动开放此模式。P0 要实现这个拒绝条件，不承诺已经补齐完整 PIT 数据库。

## 四、需要新增的数据实体

以下是接口与持久化设计，尚未实现。优先新增版本化模型和适配器，保持旧 `CasePack`、冻结实验和旧 API 可读。

| 实体 | 必须保存的内容 | 不能混淆的含义 |
|---|---|---|
| `ResearchTask` | 租户、创建人、问题、公司集合与选择理由、期间集合、资料范围、材料模式、可得时间策略、状态和 `revision` | 任务身份由服务端解析，不从模型输出或请求里的租户字符串取得 |
| `DisclosureVersion` | 发行人、原始 URL、字节哈希、申报及修订事件、精确资产可得时间及证据、抓取时间、许可范围、`supersedes` 关系 | 申报事件不替代文件版本日期；后来的比较列可能重列，不能覆盖原版本 |
| `EvidenceItem` | 来源版本、页面／表／单元格或正文位置、必要文字片段、图像哈希、提取方法与版本 | 表格数值、正文解释和图表估读分别标注；公共片段核验与完整原始输入核验分开 |
| `ResearchObservation` | 全局观察值 ID、发行人＋披露版本＋原事实 ID、原值、归一值、财务概念、单位、期间、周历、合并及经营范围、资本开支组成、证据引用 | `reported`、`derived`、`estimated` 分开；未知范围不补齐，估计不回写披露。不同公司的 `cfo-2025` 不能视为同一事实 |
| `EvidenceAssessment` | 观察值 ID、图文规则结果、检查版本、人工采用或拒绝、理由和责任人 | 自动一致性与人工采用是两个状态；未采用数据可以展示但不进入已确认比较 |
| `ComparisonContract` | 指标、同行集合、期间对齐规则、允许的单位换算、所需口径维度、不可比处理、版本哈希 | 先固定比较定义再看结果；不通过改名单、改期间或改评分器制造好看的比较 |
| `ResearchSnapshot` | 任务版本、输入及契约哈希、采用和排除的观察值 ID、计算、可比性、缺口，以及 EvidenceAssessment／Claim／HypothesisCheck 的不可变版本和内容摘要 | 数字、证据采用决定和解释判断一起冻结；相同输入和规则产生相同语义结果，运行时间单独记录 |
| `Claim` 与 `HypothesisCheck` | 结论类型、文字、引用、公式输入、支持及反驳材料、核查问题、结果和局限 | 数值事实、引用的公司说法、研究推断、模型估计分别呈现。P0 的核查不是统计因果检验 |
| `ResearchHandoff` | 快照哈希、提交人、复核人、决定、意见、待办及后续版本链接 | 可确认“已按所列范围完成研究，仍有这些缺口”；不能把缺口消失或无法比较的数值标成有效 |

口径设计不能停在一个不透明的 `basis_id`。至少要能解释“为什么不能合并”，例如 `operations_scope=continuing` 与 `total` 不同、`capex_components=ppe` 与 `ppe_and_intangibles` 不同。原始描述及人工映射依据也要保留，避免枚举值掩盖更细的会计差别。

来源归属须由登记关系校验：观察值的发行人、披露版本及证据发行人必须对应。把 B 公司金额挂在 A 公司名下，即使单位、期间和值都相同，也应拒绝；计算引用使用全局观察值 ID，不能只用公司内的 `fact_id`。

期间对齐要使用实际日期和长度。是否允许相近财年结束日由 `ComparisonContract` 声明并经研究员确认；超出范围则仅并列展示。52 周与 53 周不能自动按日均折算成“相同口径”，更不能只按年度标签连接。

来源进入新任务时先经过显式适配。NVIDIA／AMD 实验包可以提供证据引用及未通过项目，但其历史可得性标志不能在转换中变成 true，视觉实验结果也不能直接产生审批事件。

## 五、接口和状态设计

沿用 FastAPI、现有身份解析与本地事务基础，先增加研究任务服务；本阶段不因“企业级”名称引入 Kafka、Kubernetes 或新的付费数据库。是否需要这些组件应由任务量、并发、恢复和部署需求决定。

下列路径都是**建议接口，当前不存在**：

| 接口 | 作用与约束 |
|---|---|
| `POST /api/research/tasks` | 建立任务与比较契约；使用服务端租户身份和幂等键，同键不同内容返回冲突 |
| `POST /api/research/tasks/{id}/observations` | 引用已登记材料中的候选事实；不能传任意本机路径或让 Agent 任意下载 URL；写操作带任务版本 |
| `POST /api/research/tasks/{id}/snapshots` | 冻结候选材料，执行可比性和确定性计算；返回快照及逐项缺口，不自动批准 |
| `GET /api/research/tasks/{id}/snapshots/{snapshot_id}` | 返回同一版本的表格、原文定位、计算和假设状态，作为页面及导出的共同数据源 |
| `POST /api/research/tasks/{id}/checks` | 仅在可编辑状态、当前 revision 保存核查及证据；产生新 revision 并要求重新生成快照，不能修改已有快照中的判断 |
| `POST /api/research/tasks/{id}/actions` | 提交、独立复核确认或退回；检查版本、快照哈希、身份分离及所有必答项目 |
| `GET /api/research/tasks/{id}/snapshots/{snapshot_id}/export` | 导出带输入、公式、引用、缺口和复核状态的底稿；原始受限材料不随导出公开 |

状态可采用 `draft → ready_for_review → in_review → reviewed/returned`。硬错误（错误单位、断开的引用、被拒绝事实仍参与计算等）阻止提交；资料确实缺失可以作为 `not_assessed` 项交接，不能生成确定结论。提交必须绑定最新 revision 和包含数字、证据采用及假设判断的完整快照哈希。提交后 `checks` 也不可编辑；退回后修改生成新 revision 与快照。新材料标记受影响的 claim 并开启新版本，旧 `reviewed` 快照保持原结果。

未来的 Agent 通过带任务和快照身份的工具搜索、计算及提出假设，租户、时点和范围在工具层过滤；模型不能批准任务、改冻结测试集或披露值。P0 先用模板和人工假设验证任务，不依赖语言模型才能交付。

## 六、多模态、时序与因子如何服务同一个问题

| 方向 | 在这项任务里负责什么 | 进入条件与评价 |
|---|---|---|
| 多模态证据 | 表格给数字，正文与附注给范围和解释，页面图像帮助发现串列、符号与版面问题 | P0 复用已有原页和核对结果；不能仅凭 OCR 一致让事实获批。P1 比较文本检索与视觉检索、表格解析；分别测证据找全、单元格对齐、数值与单位、最终结论 |
| 时间与版本 | 说明“哪个期间发生变化”“哪一版材料支持判断”“当时是否能够知道” | P0 保存当前材料快照并阻止未经证明的历史使用；P1 补齐多公司多期版本和发布时间。新修订只影响新快照 |
| 可解释因子 | 把“现金流持续弱于经营规模”等想法写成带输入引用的候选特征 | P0 只有描述性变化与待检验假设。收入、资产等分母缺失或范围不同则不算；以后保存公式、时点、缺失掩码和口径，不把观察指标叫 alpha 或 PD |
| 现金流预测 | 在研究底稿中检验“这个线索能否帮助估计后续现金流” | P1 先有合格季度面板、目标首次披露标签和时间外切分，再跑去年同季、统计、线性及树模型；P2 才比较文本、多模态或时序模型增量 |

P1 预测实验另行冻结观察时点、目标期间、首次披露标签、可用特征、公司及时间切分、指标和成本；预测与 nowcasting 分开。标签实际公布后才进入训练，归一化和特征选择只拟合训练段。

同一个假设可先经历“有没有原文支持”，再经历“是否能在样本外预测”。二者不能互相替代。两家公司两期年度仅够验证工作流和财务口径，不足以宣称预测、因子有效性或论文结论。

方法背景沿用已注明日期及核验边界的[平台研究方案](../11-financial-research-platform.md)、[技术说明](../12-project-story-and-technology.md)与[时序因子计划](../10-time-series-and-factors.md)。本轮不新增“某篇论文已经适配本项目”的结论。同行调研的论文、产业案例和工具是设计参照，未在本仓库同任务运行的方法仍记为候选。

## 七、验收必须覆盖整份研究

先冻结小型任务集：材料清单、参考结果、支持及反驳片段、故意设置的错误、允许输出和不能作出的结论。合成反例与真实材料分开标注，同一表头或同一公司多行不当作独立公司样本。

| 场景 | 必须看到的结果 | 留下的验收证据 |
|---|---|---|
| 两家公司均有可比材料 | 形成完整比较表、公式和可定位原文，另一身份可复核 | 同任务 UI、API、导出逐字段一致及复核轨迹 |
| 同叫 FY2025 但结束日错位，或 52／53 周、单季／累计不一致 | 展示实际期间并按契约处理；不能隐式年化或只按年度标签连接 | 可比性拒绝及排除记录，每个操作数的期间、单位、公式 |
| 持续／终止经营、合并范围或资本开支组成不同 | 阻断受影响比较或公式；原值可看，无证据桥接不排名 | 口径、原始标签和排除清单，不出现混口径 FCF／现金转化 |
| 只有申报日，没有当前字节历史证明 | 当前材料模式可读；历史时点模式拒绝 | 两种模式的来源范围与明确缺口 |
| 新报告重列往年比较数 | 新旧值与版本并存；已审底稿不变 | 原快照哈希、新修订关系和受影响 claim 列表 |
| 单侧缺期、真实零或负 CFO、识别结果有疑点 | 缺值不填零，不输出误导性增长率；疑点保持待核，不能挑识别器自动采用 | 空值及阻断原因、各方法结果、原页和人工处理 |
| 两家公司都有 `cfo-2025`，或错挂公司来源 | 不碰撞、不串公司；拒绝与登记归属不符的引用 | 全局观察值身份与发行人／版本／证据对应检查 |
| 假设有引用但引用不支持原因 | 保留待查或被反驳，不生成“已经证实”的解释 | 逐条支持／反驳／缺口和研究员判断依据 |
| 资料内含改变任务或批准的指令 | 作为材料内容处理，不影响工具权限与状态 | 固定攻击材料、实际工具调用及最终任务状态；接模型后另测真实攻击效果 |
| 提交后修改假设或资料、双人并发、重复请求 | 数字和判断一起锁定；陈旧版本失败；退回修改生成新快照；同键重试不重复创建 | 含 claim／assessment／check 的快照摘要、幂等和版本测试 |
| 切换租户、身份或截止策略 | 不能读取其他任务；旧页面结果清空，来源与图片版本保持一致 | API／界面回归，含无权限读取及导出 |

软件验收报告列出上述场景通过与失败，不称为模型准确率。模型阶段分别报告检索证据覆盖、抽取及算术错误、无依据结论、错误放行、合理拒答、引用支持与任务完成率，并注明题目、公司和文档分组。研究员试用时再对相同材料、相近难度任务比较用时、返工及错误放行；没有真实参与者，就只登记技术验收，不编造效率改善。

## 八、按交付依赖推进

### P0：一个完整的同行研究任务组

1. **材料与契约。** 先选择有合法原始披露的同业对，补足两期可比年度及必要解释材料；登记范围、版本、许可与未确认事项。建立新研究实体和旧包适配，不改冻结实验。
2. **比较与证据。** 实现同一快照中的数值差异、可比性矩阵、原文跳转、缺口和受影响项目。当前模板生成数值说明，解释由研究员填写及核查。
3. **任务与交接。** 接入租户及角色、候选事实采用、固定快照、假设核查、独立确认／退回和导出。把现有分开的页面入口收进这一条研究路径。
4. **整体验收。** 跑上表中的正反例与界面／API／导出对照；交付一个可从建立任务到复核完成的演示，并保留失败和剩余问题。

四项构成同一交付组，不以只新增模型名、一个比较图或一份计划作为 P0 完成。若现有两家公司材料仍不可比，先交付明确不可比的研究结果，同时补齐合格材料；不能为了演示“成功”降低口径要求。P0 不需要租 GPU。

### P1：数据和评测达到研究条件

扩展公司、行业、年度与季度，同时建立修订链及财年映射；留出没有用于规则调整的发行人与未来时间段。增加跨页、正文解释、图表及真实扫描件任务，采用文档／公司分组，避免把同页多行当大样本。先完成同材料的人工参考和简单工具基线，再决定是否接入检索、表格模型或语言模型。数据规模按有效独立样本、标签覆盖及误差稳定性判断，不用任意行数门槛充当充分性证明。

部署、SSO、外部审计留存、备份恢复与并发容量作为试用前的工程条件另行验收。当前 API-key、SQLite 和本地演示基础不能直接改写为金融机构生产能力。

### P2：训练需要同时满足的条件

有合法可训练的数据、冻结且独立的评测、可运行的训练及评估脚本，并且强提示／检索／统计或树模型基线暴露了可重复的能力缺口。先测小任务的内存、吞吐、成本和失败，再提出是否需要单张 A100 40GB、预计租期及预算。没有增益应保留负结果，不将缺少实际增益的模型纳入发布版本。

本设计不启动训练、收费 API 或租卡。数据和流程改进均可先在已有 CPU 环境推进；新增费用仍需用户明确授权。

## 本轮交付边界

已完成的是：读取现有实现、识别跨模块断点、确定一个企业研究任务、设计数据实体和接口、给出任务级验收及分阶段依赖。本文没有运行新模型、添加研究接口、取得新财务数据、开展用户试用或证明金融预测能力。

对外材料可以引用本文说明“下一步怎样做”。只有 P0 的实现合并、任务运行与验收完成后，才能把“多公司研究闭环”写入已实现功能。
