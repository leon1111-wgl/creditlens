# 用真实披露复演三段企业研究交接

日期：2026-10-25。场景登记：`data/demo/research-scenarios.json`。

这三段故事把当前功能串成一项完整工作：分析员收到问题，选择材料、记录采用或拒绝理由，提交冻结底稿，交给另一职责身份复核，再保留交接结果或退回意见。

业务问题、团队、角色和工作事件均为模拟。财务金额来自项目已登记的微软与苹果官方披露，不在场景配置中编写数值。这不是客户案例或真实合作项目，也没有真实用户效果、节省工时或生产部署的声明。脚本中的“复核员”是独立的模拟身份，不能称为真实人工作出的审阅。

## 故事一：利润增加，经营现金流为什么下降

模拟研究团队收到问题：苹果 FY2025 净利润增加，为什么经营现金流却下降？分析员需要先把能核对的内容交出去，避免把猜测写成解释。

底稿使用官方现金流调节资料。苹果净利润较 FY2024 增加 18,274 百万美元，经营现金流减少 6,772 百万美元；这两个数由登记资料的年度差计算得到。附件保留原表中的净利润、净利润调节项、经营资产负债变化和合计，复核人能追到原行，并检查各项贡献相加是否等于 CFO 变化。

分析员把税款、结算、回款等可能的后续研究方向留为 `pending`，没有凭调节表确认这些原因。模拟复核员确认资料及会计分解可交接，任务终态是 `reviewed`。它确认的是底稿范围，不是投资、授信、付款或因果结论。

## 故事二：数据是真的，比较用途却不成立

另一份模拟初稿想因两家公司都标 FY2025 就给现金流表现排名。问题在研究用途：微软与苹果的实际年度结束日、日历和经营结构不同，也不是本任务已经建立的严格同行。

系统从第一次提交起就只提供并列展示，排名始终为空；演示没有伪造系统算出了一个错误排名。模拟复核员退回的是初稿文字中不当的排名提议。分析员随后补上实际期间、指标范围及不可排名的局限，重新提交，另一身份确认后进入 `reviewed`。

这段流程有两个不同快照。第一次退回的内容与记录保留，第二次确认只绑定修订后的快照。不能用修改后的文字覆盖先前审阅，也不能把同意修订稿理解为建立了跨公司可比性。

## 故事三：有官方数值，仍可能不适合这个问题

模拟预算研究想把苹果 FY2025 固定资产现金支出这一行作为当年全部资本投入。分析员拒绝把该观察用于这个更宽的问题：PPE 现金支出不能单独覆盖非现金租赁新增、无形资产及其他投资范围。

原披露数值、来源和定位完整保留；拒绝的是研究用途，不是判定官方数值为假。其余观察只按原定义采用。该公司资本支出的相关年际计算保持 `blocked`，缺少的材料不估数、不补零。

模拟复核员退回底稿，要求补定义与附注，最终状态是 `returned`，假设为 `not_assessed`。这是正确执行了保留待补的流程，不是复演失败，更不能写成已批准。

## 材料来源与边界

- [Microsoft FY2025 official annual report](https://microsoft.gcs-web.com/static-files/9640e86d-a99f-4502-934d-1d3c883fa786)：使用已登记 CFO/PPE 现金支出及经营现金流调节行。
- [Apple FY2025 official Form 10-K](https://s2.q4cdn.com/470004039/files/doc_financials/2025/ar/_10-K-2025-As-Filed.pdf)：使用同样范围的已登记事实。
- 三个场景共用旧 8 项财务观察；前两个场景另外附加 52 项有符号经营现金流资料，第三个保留旧版不带附件的流程。
- 场景配置只保存问题、步骤、职责及事实引用，不保存合成财务金额。执行时由服务器材料适配器解析真实全局 ID、来源哈希和金额；未知引用会拒绝。
- 资料是固定 FY2025 报告及比较列，不是实时信息，也未证明当前 PDF 字节在历史时点可得。经营现金流调节项不是因果模型，更不是收益或信用预测。

## 如何复演与检查

```powershell
python scripts/replay_research_scenarios.py
python -m unittest tests.test_research_scenarios
python scripts/verify_research_export.py .run/reproductions/research-scenarios/exports/profit-cash-flow-handoff.json
```

默认 SQLite 为 `.run/reproductions/research-scenarios/replay.sqlite`，导出目录为同级 `exports/`。可用 `--database` 和 `--output-dir` 明确指定另一组隔离路径；两者必须都是新路径，重跑不会覆盖已有数据库或输出。脚本不打开应用的 `data/` 数据库，也不接受输出落入公开资料目录或登记的原页目录。数据库不加入公开仓库。若材料变化等原因使流程中途拒绝，脚本返回结构化错误和非零退出码；已创建的本地输出保留，修正后应选择新的隔离路径，不自动删库或覆盖。

复演只调用 `ResearchTaskStore.create/update/act/export` 等公开接口，按真实修订号与快照哈希推进，不直接修改 SQL 状态、不跳过提交或权限检查。模拟分析员和模拟复核员为不同身份，属于明确标识的模拟租户。

输出包含：

- 三份最终冻结底稿，每份仍是原 Store 导出结构。
- 第二个场景的首次退回底稿，放在 `history/`，便于核对修改前后。
- `manifest.json`：登记场景配置摘要、模拟来源说明、角色、步骤事件、全部快照、导出文件哈希及官方来源版本。

四份导出在写出前均通过已有离线一致性检查器。它检查内部哈希与绑定，不是数字签名、来源验真或真人身份验证。步骤和预期结果确定，但任务 UUID、时间戳和导出字节并不固定，不能声称每次复演文件完全一致。

## 本实验验证

实际使用新隔离 SQLite 完成三段流程，结果依次为 `reviewed`（1 快照）、`reviewed`（2 快照）、`returned`（1 快照）。12 项测试通过，覆盖真实方向差异、两版底稿及退回记录、拒绝事实仍保留而比较阻断、全部导出哈希、模拟身份说明、新旧输出隔离、拒绝覆写、未知事实引用及材料不可用时的结构化拒绝。

这些结果证明当前工作流能按既定规则复演三种交接情形。它们没有证明产品已在企业落地，也没有把模拟独立复核变成真实客户的批准。
