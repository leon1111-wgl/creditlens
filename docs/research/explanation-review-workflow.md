# 新公司说明怎样补进研究底稿

2026-10-25。原研究底稿已经批准，后来补到一段公司的现金流说明，不能直接把新段落塞进旧导出，再沿用以前的批准。本轮新增独立补充底稿：绑定原研究版本，保存这次新增的说明，重新记录采用决定，再交给没有参与编写的人确认。

本分支实现的是 [ExplanationReviewStore](../../creditlens/explanation_review_store.py)。证据与离线核验由[附件契约](explanation-evidence-contract.md)提供，API 和界面由主分支接入。这里的身份和业务过程用于开发演示，没有真实金融机构试用或经营原因验证结果。

## 一次补充怎样完成

1. 原研究任务必须是 `reviewed`。分析员用明确的父任务 revision 和快照摘要建立补充，服务端在同一数据库事务中读取父底稿及批准记录。版本不一致就要求重新绑定。
2. 系统取得当前登记的公司说明，并保存完整父导出、来源、精确数字与舍入关系。新增说明一开始是独立草稿，没有继承父底稿的批准。
3. 每条说明选择“作为公司陈述采用”“拒绝”或“仍需证据”，写至少 10 字理由。采用只允许在关联两期 CFO 均已采用、数值按登记精度一致时进行。仍需证据也能提交，以便交接明确的缺口。
4. 提交前必须覆盖全部说明，并用至少 10 字写清范围与限制。系统重新检查父版本、父导出及当前登记资料，然后把证据、决定、文字说明、贡献者一起冻结成新快照。
5. 独立复核人可以确认或退回。确认的范围始终是公司陈述的收录和适用范围，不能变成“经营原因已独立证实”。退回后修改并重提，会产生另一份快照。

原研究作者、编辑者和提交人，以及任何参与补充创建、编辑或提交的主体，都不能审核这个补充。换成 reviewer 角色也不会改变同一用户的身份。原研究的独立复核人若没有参与编写，可以再复核补充；若后来参与了补充编辑，就不能审核新版本。

## 保存与导出哪些内容

新模块使用原 `ResearchTaskStore` 的 SQLite 连接和事务管理器，新增 `explanation_reviews`、`explanation_review_snapshots` 两张独立表。它不会更新父任务或父快照表。

父导出只保存一份，在 `evidence.parent_export` 中；顶层保留 `parent_task_id`、`parent_revision`、`parent_snapshot_sha256` 和 `parent_export_sha256` 方便核对。证据、来源和父版本均来自服务端，客户端不能提交一份自写的 evidence 或把采用范围改成因果结论。

| 接口 | 作用 |
|---|---|
| `list(task_id, actor)` | 返回同租户父任务下的补充摘要 |
| `create(task_id, actor, payload, idempotency_key)` | 用父版本和快照摘要创建独立草稿；同键同请求重试返回已有记录 |
| `get(review_id, actor)` | 返回当前内容、当前快照及历史快照元数据目录 |
| `update(review_id, actor, revision, decisions, coverage_note)` | 只在 draft 或 returned 修改决定与说明 |
| `act(..., action, note, snapshot_sha256)` | 提交、确认或退回；所有动作意见至少 10 字，复核必须匹配快照摘要 |
| `export(review_id, actor, snapshot_id=None)` | 导出所选不可变快照及仅属于它的复核记录 |

API 可复用 `ExplanationReviewCreate`、`ExplanationReviewUpdate`、`ExplanationReviewAction`。采用决定的请求只有 `entry_id`、`decision`、`note` 三个字段；服务端添加固定的 `support_scope="company_statement_only"`，不能让客户端改写。

读取、导出旧补充不重新访问当前资料目录。若公司说明后来改版或本地目录暂时不可用，会阻止新创建与新提交，但已有草稿和快照仍能按保存版本查看。相同幂等键的既有创建请求也是读取原记录，不会偷偷生成另一份来源不同的证据。

导出明确区分所选快照和当前草稿：旧快照不会混入后来修改的决定、说明或批准。父完整导出仍保留原样，新补充有自己的快照和复核历史。

## 如何防止错审和覆盖

写操作使用 `BEGIN IMMEDIATE`，在同一事务中检查父记录、预期 revision、子记录和快照。更新另带 revision 条件，同一版本的两个编辑请求只能有一个成功；数据库忙时返回可重试的冲突。跨租户查询按不存在返回，不能用另一补充的快照 ID 导出内容。

自由文字仍按用户填写保存，本轮没有语言模型判断文字真假。即使某人在理由中写“已经独立证实”，也不能更改固定的采用范围、来源限定或 `independently_verified=false`。这不表示系统完成了文字语义审核；显示与导出仍须把它作为填写者意见。

存储摘要和离线契约检查能够发现内容、来源、版本和摘要不一致。它们不是外部数字签名，也不能阻止有数据库管理权限的人同时改写全部内容和摘要。demo 身份是流程模拟，真实身份认证沿现有 API 权限模式处理，机构部署与运维验证另行建设。

## 已运行的验证

```bash
python -m unittest tests.test_explanation_review_store -v
```

本分支实际运行 20 项专属测试，全部通过。测试使用真实登记的小型财务资料及公司说明，但角色、操作和数据库均为开发用临时实例。覆盖完整创建、采用、提交、确认、退回重提、缺口交接，以及以下关键边界：

- 为父任务与父快照表安装拒绝任何写入的 SQLite 触发器，子流程仍能完成，父导出内容不变。
- 父、子所有贡献主体换角色后仍被拒绝自审；曾经复核但后来参与编辑的人不能复核新版本。
- 旧子快照及对应复核记录在重提之后保持相同；其他子稿的快照 ID 和其他租户都不能访问。
- 来源目录删除或改写、父版本变化阻止新冻结，旧导出仍可读取；资料不被自动重取或改写。
- 缺决定、短说明、未采用的 CFO、自填 evidence、伪造采用范围、非有限值及陈旧 revision 被拒绝。
- 同 revision 并发只有一次成功；忙锁可重试；返回对象被修改不会改数据库；存储摘要损坏被发现。

本轮不新增模型调用、OCR、网页抓取或训练。API、浏览器流程、下载文件一致性和完整回归由主分支整合验收，不据这里的存储测试宣称它们已经完成。
