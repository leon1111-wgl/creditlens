# 产品和服务毛利率变化：先核对加总，再拆开贡献

研究员看到公司总毛利率变化时，常需要先回答一个有限的问题：是收入更多来自原本毛利率较高或较低的分类，还是各类业务自己的毛利率发生了变化？本轮把这一步做成可复算的会计底稿，并保留每个金额的原页定位。

实际材料只有两个公司案例：微软、苹果各自的FY2024到FY2025。它们使用同份FY2025报表的比较列，产品与服务是收入和成本的列示分类，**不是经营分部，也不作两家公司之间的排名**。持续／终止经营细分保持未知。

## 金额从哪里来

[登记材料](../../data/examples/margin-source-observations.json)包含28项收入、成本、总毛利金额。主开发查看了既有微软第50页和苹果第32页的原页图，并结合此前保存的OCR父行整理出处；这是工具辅助参考，独立人工确认仍为pending。

每年登记两类收入、总收入、两类成本、总成本和总毛利，共7个金额。分类毛利由收入减成本得到，不能写成公司逐类披露了毛利。两公司、两年度的28项金额重复参与加总和分解，仍只算两个开发案例，不是28道独立模型评测题。

有些OCR父行包含相邻美元符号，例如`63,946 $`。金额原值来自本轮原页查看，定位框则完整保留原OCR父行框及原文字，不按预期数值裁框。它是近似回查位置，不能拿来声称精确金额定位已通过。百万美元单位沿用既有来源与收入登记，不能仅凭一个`$`符号推定币种。

适配器将新材料绑定到旧事实包的规范摘要、报告来源、收入金额、日期、单位及原图/OCR登记，并复核既有Note 1合并范围依据。新来源文件固定UTF-8 LF字节摘要和规范JSON摘要；旧支持文件使用规范JSON摘要，避免把Windows换行差异误当成财务版本改变。读取前后比较原始文件快照，发现过程中发生变化就停止。这不等于重新验证PDF字节或来源真实性。

## 怎样分解

先逐年要求两类收入加总等于总收入、两类成本加总等于总成本、总收入减总成本等于披露总毛利。金额核对必须精确相等，不用小容差掩盖漏项或错口径。

定义某类收入占比为`w`，该类毛利率为`m`。从基期0到本期1，采用对称分解：

- 收入构成贡献：`100 × Σ[(w1 − w0) × (m1 + m0) / 2]`。
- 分类自身毛利率贡献：`100 × Σ[(m1 − m0) × (w1 + w0) / 2]`。

两项相加对应总毛利率的百分点变化。这种对称口径把交叉变化平均分配；换成其他分解约定可能改变两项分配，因此它不是唯一的经济解释，更不能据此断定价格、销量或某项成本是变化原因。

计算使用固定80位Decimal上下文，额外用独立的精确分数运算核对总变化和每个分类的贡献。显示保留六位小数，全精度残差与显示舍入差额分别记录。收入必须大于零；负毛利可以保留原符号，负成本则超出本轮解释范围而被拒绝。

## 本轮实际结果

| 公司自身比较 | FY2024总毛利率 | FY2025总毛利率 | 总变化（百分点） | 构成贡献（百分点） | 分类毛利率贡献（百分点） |
|---|---:|---:|---:|---:|---:|
| 微软 | 69.764444% | 68.823742% | -0.940701 | -0.411185 | -0.529517 |
| 苹果 | 46.206350% | 46.905164% | +0.698814 | +0.616372 | +0.082442 |

四个年度列的收入、成本及毛利恒等式均闭合；精确分数分解的残差为零。微软两项贡献各自显示六位小数后，与显示总变化相差0.000001个百分点，报告保留这项舍入差额，不修改贡献数凑齐。微软日历财年有365／366天差异，系统保留原披露全年金额并提示，没有按日年化；苹果两期均为364天周历年。

这只说明登记金额及所选会计公式互相一致。不是OCR准确率、独立人工标注结果、未见公司泛化或经营原因验证。

## 失败也在分母里

19个合成开发控制与两个登记案例分别统计。三项正例检查仅构成变化、仅分类毛利率变化，以及负毛利是否正确保留；16项反例覆盖收入／成本／毛利加总错误、缺失或重复分类、分类定义改变、公司或来源混用、错币种单位或货币符号、错期间、未披露金额、零分类收入、负成本、显示负号冲突和分部范围混用。全部符合固定预期，拒绝项保留具体原因，未披露金额没有被补成零。

21项专项测试通过，包括逐字段重放、来源与实现版本变更、同计数篡改、原页身份、显示舍入、独立分数核对、调用方Decimal精度／异常陷阱污染及安全输出。保存报告约1.14 MiB，只包含登记事实、必要定位和计算控制，不含完整PDF、页图或完整OCR。

## 复算和交接

```powershell
python scripts/evaluate_margin_bridge.py --output margin-bridge-new.json
python scripts/evaluate_margin_bridge.py --verify-saved
python -m unittest tests.test_margin_experiment
```

输出只能在`.run/reproductions`直接新建JSON，同名文件拒绝覆盖。`--verify-saved`重新加载固定登记材料，复算两个公司案例及所有控制，并逐字段核对[保存报告](../../artifacts/margin-bridge-report.json)；它不会重新识别图片或核验完整OCR。

`load_margin_bridge_snapshot(root)`向主分支API提供同一已核对报告及其字节摘要；`margin_image_metadata(snapshot, case_id)`从该快照返回原页身份，便于页面定位。图像字节仍须由原有预览服务核对，不把元数据返回当作已读取图片。API和浏览器整合由主分支另行验收。

本轮没有下载新数据、调用模型或付费训练，独立人工金标准仍为0。后续若要解释经营变化，需要再登记公司披露的解释、相关附注和可检验假设，不能把本轮两个会计贡献改写成已经证明的原因。
