# 写入成功后丢失响应：事务内回执

研究底稿或解释补充稿的修改、提交、批准和退回，可能已经保存成功，但浏览器没有收到响应。过去用旧revision重试会收到409，使用者无法直接分辨“未成功”与“成功但回包丢失”。本轮给这四类写入增加可选的幂等请求键：相同请求可以取回第一次完整响应，不再执行一次业务动作。

## 接口与兼容

两个store的 `update` 和 `act` 参数末尾增加 `idempotency_key: str | None = None`。研究底稿的 `update` 中它位于已有 `bridge_review_note` 之后，`act` 中位于 `snapshot_sha256` 之后；解释补充稿同样只追加参数。不带键保持原CAS、状态机和返回内容，不修改旧v1／v2快照、旧冻结报告或已有创建接口的幂等规则。

有键时要求字符串长度8至128且不全为空白。键作为不透明字符串精确保留。请求正文使用既有请求模型规范化（包括已有的首尾空白处理、默认值、revision和snapshot摘要），然后绑定租户、用户、角色、实体类型、实体ID及具体动作。它不是只对“新修改的几个字段”计算摘要。

## 同一事务保存

独立SQLite表 `research_write_receipts` 的主键是 `(tenant, request_key)`，两个实体类型共享同一租户的键空间；另一租户可以在自己的对象上使用相同键。表内保存规范请求绑定、首次完整响应及各自摘要和整条回执绑定摘要。没有另外开连接提交。

调用顺序为：校验当前角色，加载同租户对象并检查存储完整性；批准／退回还先检查当前贡献者限制；随后查找回执。相同键但请求、身份、角色、对象或操作不同，409且无业务副作用。完全一致时返回已保存响应；未命中则执行原有revision／状态／来源／审批检查，在原 `BEGIN IMMEDIATE` 事务内完成业务修改、事件、快照、完整响应构造和回执插入，再一起提交。

回执写入失败会使已经执行的业务变更、事件和提交快照一起回滚；业务先失败也不占用请求键。SQLite写事务串行化让并发的相同请求只产生一份业务变更，后一个请求读取同一回执。服务对象重建后仍可读取数据库中的回执。

## 原回执不是最新版本

回放返回第一次保存的响应，包含当时的revision、事件和快照列表。后续业务可以已经推进，不把当前内容混入旧响应，也不加一个随重试改变的 `replayed` 字段。调用方需要最新状态时，应另行GET。界面不能把较旧的回执当成当前最新版本，或收到旧提交回执后再次自动提交。

回放不重新访问在线来源、重新生成解释或再次审批，因为原事务已完成。但当前身份、角色、同租户对象可读性、对象存储完整性，以及复核者的当前贡献者限制仍要通过。删除对象、改变可用角色或损坏业务记录不会因存在旧回执而绕过检查。

## 完整性与错误

读取回执时检查规范JSON、重复键／非有限值、请求／响应摘要及整条回执摘要。响应的实体、租户、revision、动作和原事件必须对应绑定，原事件列表必须仍是当前对象保留历史的前缀。损坏时固定返回 `write_receipt_integrity_failed`，不回显正文。键冲突为 `write_receipt_conflict`；非法键为422 `invalid_write_receipt_key`；回执无法保存为503 `write_receipt_storage_failed` 并回滚。

这些是本地一致性检查，不是签名、防管理员重写或外部审计锚。能同时修改业务、回执和摘要的管理员不在保证范围内。回执保存在本地应用数据库，不进入公开仓库；本轮没有加入自动清理策略或宣称永久外部备份。

## 验证和不包含的行为

专属测试使用隔离SQLite和真实已登记材料、模拟身份，覆盖两个store的修改／提交／批准／退回、响应丢失后的同键重试、更高版本下的旧回执、重建服务、离线来源、身份／租户／贡献者限制、同键冲突、回执损坏、并发请求及SQL故障触发的原子回滚。旧父稿导出、现金流v2内容和解释范围不改变。

这是服务端重试能力。本轮不表示浏览器已经能跨刷新、关闭或换设备自动找回未完成请求。网络失败后，客户端必须保留原请求键和原规范请求，才可以请求同一回执；不应生成新键后自动重放旧批准意图。
