# 保存成功但没收到响应，怎样安全重试

研究底稿或公司解释补充稿已经保存成功，页面却没收到响应时，用户无法判断应当继续还是重新提交。本轮为四个写入入口增加可选的请求键：研究底稿与解释补充稿各自的保存、提交／复核动作。同一个写入意图带相同键再次发送，服务端返回第一次完整响应，不再创建事件、版本或快照。

业务修改和回执存入同一SQLite事务。如果回执没能保存，业务修改也回滚。新请求仍检查当前身份、租户、权限和版本；重试键不能变成跳过权限或自审规则的凭证。同租户内把一个键用于不同主体、角色、对象、动作或请求内容会冲突，调用方必须为新意图生成新键。未提供键时保持此前的版本校验行为。

## 这轮如何验证

复演只使用现有微软与苹果官方登记的小型材料，在临时SQLite数据库中建立一份研究底稿及一份解释补充稿。身份、采用意见、固定时间和固定ID都是模拟数据，临时数据库结束后删除，不写主业务数据库。

两份底稿分别完整执行保存、提交、退回、修改、重提、确认，共12个成功写入意图。每次先让服务端提交，再在调用端模拟丢弃成功返回，重新发送完全相同的键、正文和身份。验证原完整响应相同，当前事件、版本和快照没有重复增加。随后将版本推进，再重放之前的保存及提交请求，确认返回的是当时的响应，服务端当前状态没有被回退。

另外使用隔离数据库的触发器模拟回执写入失败，检查业务版本、事件和快照整体回滚；暂时损坏一条保存回执的正文但保留原摘要，确认拒绝重放且不再次写业务。材料构建或公司解释登记暂时不可用时，已完成的回执仍可取回，新提交会停止。重新创建服务对象后，也能从同一临时数据库取回此前的回执。

API测试另外覆盖四个实际HTTP写入入口：包括完整往返、相同键并发请求只生成一次提交、错误主体和跨租户访问、同键改正文、无键旧行为、请求头长度、存储失败和损坏回执。测试客户端会刻意不把第一次成功响应当作业务已确认，并保留测试用副本进行比较。这是可控故障模拟，不是实际断网、浏览器崩溃或生产网络测试。

正式复演的56项检查全部通过：12个成功写入意图对应12条回执，研究底稿与解释补充稿各保留2个快照。9组API测试通过，包括并发提交、更新及提交失败时的事务回滚。实际HTTP测试发现首次响应与重放的JSON键顺序不同，已修正带键写入的首次返回序列化；现在完整HTTP响应字节一致，未带键的旧路径保持原样。公开报告为17,495字节。

## 结果如何记录

公开报告只记录固定模拟流程的检查结果、响应摘要、版本／事件／快照数量，以及旧导出前后相同的摘要。不会把整个研究底稿、回执数据库或密钥复制到产物中。报告绑定执行源码与材料版本，复演时逐字段比较，不用通过数替代具体状态和旧导出不变的检查。

旧快照的财务内容保持原样；公司解释的确认仍只确认“收录公司说法及其适用范围”，不证明经济原因。没有新的OCR、模型调用、下载、费用或独立人工标注。

## 使用与边界

页面或API调用方应在发送写入前保留同一个请求键、请求体、对象和身份。如果结果未知，只能重试原意图；编辑了内容就应另起请求。已拿回旧响应后还需要重新读取当前对象，不能把旧版本显示成最新状态。切换身份后也不能自动拿旧键代替新身份提交。

复演命令默认只输出小摘要；若保存报告，只能创建 `.run/reproductions` 下的新JSON：

```powershell
python scripts/replay_research_write_retry.py --output research-write-retry-local.json
python scripts/replay_research_write_retry.py --verify-saved
```

本轮只恢复已有已提交写入的回执，不承诺在提交之前失败的请求已经受理，也不提供异步队列或自动后台重做。回执摘要检查针对不一致和损坏；能同时重写业务、回执与所有摘要的数据库管理员不在此防护范围。企业使用价值是避免不确定结果下重复操作，尚未测量真实团队节省的时间或线上故障率。
